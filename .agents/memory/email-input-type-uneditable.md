---
name: Auth email inputs blocked by native browser autofill
description: Recurring bug family — native browser credential-manager UI (Chrome autofill, Safari/iCloud Keychain, mobile) recognizes email AND password fields by form shape/attributes (not just type/autoComplete) and captures the keyboard, sometimes blocking paste too, sometimes flickering typing on and off. Attribute-only mitigation is insufficient. readOnly-until-focus was an earlier "reinforced fix" but is now SUPERSEDED — see step 5 — by an uncontrolled-input + submit-time-DOM-resync pattern. Applies to any credential-shaped field (email, password, confirm-password), not just email.
---

**Rule:** ALL credential-shaped inputs site-wide (email AND password fields) — not just auth pages — must minimize autofill-detection signals AND tolerate autofill writes that bypass React:
- No `type="email"`, no `autoComplete="email"`/`inputMode="email"` (use `autoComplete="off"`, `inputMode="text"`) for email fields. Password fields keep `autoComplete="current-password"`/`"new-password"` (needed for legitimate password-manager UX — the goal there is not blocking the manager, just not letting it block the user).
- DOM `name` must not contain "email" (override after the RHF `{...field}` spread — RHF Controller is ref-based), `data-lpignore` + `data-1p-ignore`.
- Placeholder must not contain `@` or an email-shaped string (e.g. `nombre@email.com`) — browsers' autofill heuristics scan placeholder text too, not just attributes. Use plain text like "Introduce tu correo".
- No `autoFocus` on the field — auto-focusing on mount is exactly the moment the autofill engine hooks the field during hydration.
- **~~readOnly until first focus~~ — DEPRECATED, do not use (see step 5 below).** Was: render the input `readOnly={locked}` with `locked` initialized `true`, unlocked via `onFocus`. Superseded 2026-07-30 by the uncontrolled-input pattern.
- **Uncontrolled input, no readOnly at all (current fix, confirmed on login.tsx, ported everywhere 2026-07-30):** drop the `value` prop, use `defaultValue` for the initial value, keep `onChange` wired to sync app state (for live UI like button-disabled/error-clearing), and re-read the *live DOM value* via a `ref` at the moment of submit — don't trust the React state, which may be stale if autofill wrote to the DOM without firing an `input` event. For RHF fields this is `syncDomValueIntoForm` (reads `formEl.elements.namedItem(domName).value`, calls `setValue` right before `handleSubmit`). For plain `useState` forms without a `<form>` element (e.g. dialog "Guardar" buttons), attach a `ref` directly to the input and read `ref.current.value` inside the click handler instead.
- Custom `onBlur` resync (`if (e.target.value !== form.email) set({ email: e.target.value })`) is no longer necessary once the submit-time ref-read is in place, but harmless if left in.

**Why:** Root cause is broader than first diagnosed, twice. Timeline:
1. Original 2026-07 diagnosis ("native autofill widget captures focus on click") → attribute-scrubbing recipe (no `type=email`/`autoComplete=email`/`inputMode=email`) applied to `login.tsx` email field twice (Thu commits), user confirmed fixed at the time.
2. Recurred on `team.tsx`'s create/edit-user dialogs (different screen, same anti-pattern, never touched by the login.tsx fixes) — fixed 2026-07-11.
3. User retested `/register` email field in production on 2026-07-11 across Safari, Chrome desktop, and mobile — still 100% blocked from the first keystroke on every one, despite the attribute recipe. A total, engine-agnostic block like that isn't a per-browser autofill-dropdown quirk (those normally still let you type around the suggestion) — it's the browser/OS-level credential-suggestion UI recognizing the whole form shape and hooking the field regardless of attributes, especially with saved credentials present (a clean/sandboxed test browser reproduces no block at all, which is why testing in an automation browser without saved autofill data gives false negatives). **Fix: readOnly-until-focus recipe, added to the email fields. User confirmed this worked across Chrome desktop, Safari desktop (with Keychain), and mobile.**
4. **Same day, immediately after: user reports the *password* field on `/login` now has the identical symptom** — 100% blocked from the first keystroke, on mobile and desktop, Safari and Chrome — plus paste is also blocked (ruled out any in-app `onPaste`/`onKeyDown` handler; grepped the whole frontend, none exist — confirms this is native browser/OS behavior, not app code). The password manager doesn't even visibly prompt; it just silently eats all keyboard and clipboard input. This is the same bug class as the email one, just on a different field type that hadn't been hardened yet. Applied the same readOnly-until-focus recipe to `login.tsx`'s login password field, and preemptively to the register password + confirm-password fields (same shape, not yet reported broken, but no reason to wait for a third round-trip).

**Lesson — don't declare this bug class "fixed," only "fixed for the fields hardened so far":** every credential-shaped field (email, password, confirm-password) on every form is an independent target for the browser's heuristics; fixing one field does not fix siblings on the same form. When a "same error" report comes in again, check *which specific field* first (don't assume it's the same field as last time — it's been a different one each time: team.tsx's email, then login's password) — grep for `type="password"` and `type="email"`/email-shaped inputs across the frontend and check each one has the full recipe.

5. **2026-07-30: readOnly-until-focus itself confirmed as the recurring culprit, not just an incomplete fix.** User reported the invite-to-trip email field (`trip-travelers-tab.tsx`) intermittently "activating and deactivating" while typing — in both Safari **and** Chrome desktop, not just the iOS-keyboard failure mode this recipe was originally designed against. Root cause: toggling the `readOnly` DOM attribute on a field that still has focus (via the `onFocus={() => setLocked(false)}` handler) makes the browser's autofill/credential-manager engine re-evaluate the field on every focus event, which can intermittently swallow keystrokes right as the user starts typing — a milder, non-deterministic version of the same "engine hooks the field and eats input" problem the recipe was trying to prevent. `login.tsx` had already moved off this recipe (see [[safari-controlled-input-autofill-bug]], layer 1+2, fixed 2026-07-29) onto the uncontrolled-input + submit-time-ref-read pattern, but `team.tsx` (create + edit user dialogs) and `trip-travelers-tab.tsx` (invite dialog) still had the old readOnly-until-focus code — exactly the "same bug jumping to a different field" pattern predicted in the lesson above. Ported the login.tsx pattern to all three; readOnly-until-focus is now fully retired from the codebase.

**How to apply:** Any email field anywhere in the app follows: attributes (`autoComplete="off"`, `inputMode="text"`, `data-lpignore`/`data-1p-ignore`, no `email`-shaped `name`) + placeholder without `@` + no `autoFocus` + **uncontrolled input with submit-time ref-read** (no readOnly, ever — see step 5). Password fields keep the attribute recipe but have not needed the readOnly-until-focus treatment since 2026-07-11 hardening (`login.tsx` login + register password/confirm) — re-check those if a password field reports the same symptom, since they still use the old recipe and per step 5 that recipe is now suspect for *any* field, not just email. Current state (2026-07-30): `login.tsx` and `trip-travelers-tab.tsx` and `team.tsx` (create + edit user, email only) all use the uncontrolled+ref pattern; `login.tsx`/`team.tsx` password fields still use readOnly-until-focus (unreported as broken, but same risk). If a password field is reported, apply the step-5 fix there too rather than assuming password fields are exempt. Longer-term fix: extract a shared `<AutofillSafeEmailInput>` component so the mitigation only has to be applied and updated once instead of per-field-per-screen — five separate recurrences of this bug family is a strong signal the per-field copy-paste approach doesn't scale.
